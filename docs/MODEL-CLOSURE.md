## Goal and boundary

All four original apps remain independently deployable, with separate users, sessions, containers, databases, volumes and origins. The supported production envelope is measured small-team use, initially 50 people using each of four apps, with a 100-user burst per app. This is no claim of vendor feature parity, billion-user capacity, universal 95% fit, zero maintenance, or a perpetual security guarantee.

One optional host HTTPS gateway may serve any selected subset. Each app's backup worker is independent. A gateway is infrastructure; no app requires another OpenSW app. Local/private HTTP remains a legitimate deployment mode. Supported Docker hosts use standard protected bridge/NAT/firewall isolation; deliberate custom exposure/direct-routing/security overrides are outside this supported boundary and are not certified by the version check. Public HTTPS setup must require a configured encrypted off-host backup and confirmed first backup before claiming production readiness. Each future operator supplies their own DNS/server/storage access. This task verifies the downloadable software using real isolated ACME/S3 protocols and must label fixture scope; it does not require or claim a personal live deployment.

Risk triggers: public/authentication/privacy boundaries; runtime/config/SQLite/blob consistency; backup retention/restore; asynchronous lifecycle/unknown outcomes; source builds/upgrades; public release and active v0.1 clients. Root failure class: reporting an operational or resource state as confirmed when its canonical owner has not confirmed it.

## Canonical owners and invariants

1. **Identity and app data:** existing shared/catalog.json, per-app SQLite schema version 1, immutable metadata app+instance, row IDs/authorship/revisions, and UUID blob keys. Keep the database schema and all existing API resource shapes/catalog values unchanged unless measured evidence invalidates that decision. No journal-mode switch without evidence and a new model revision.
2. **Runtime configuration:** the app volume's state/config.json keeps exactly the current five keys `{app,instance_name,team_name,public_url,max_upload_mb}`. Installer TOML is the operator's input. Requested origin is not running origin. Retained users/content are never reseeded. App+instance remain immutable; HTTPS origin changes are explicit confirmed deployment transitions.
3. **Installer/controller:** tools/install.py owns config validation, selected Docker engine/SSH identity, app lifecycle, image/source identity, admission/recovery sequence and per-app install lock. Exactly named/labelled resources only; no global Docker context change or foreign-resource adoption. Source archives exclude actual config, SSH key, backup password/credential/CA paths and inode aliases. Unknown Docker outcome is inspected, never blindly replayed.
4. **HTTPS:** one OpenSW-owned Caddy gateway per Docker host owns 80/443 (advanced test/private ports may be explicit). Each app has its own private user bridge; only that app and the gateway join it. Apps keep loopback management ports and independent data volumes. Gateway has no Docker socket or app data mounts. Its admin API is its own localhost only. Caddy route IDs are globally unique: HTTPS application `{deployment}` and distinct HTTP redirect `redirect-{deployment}`; each server replaces only its respective ID. The controller owns ONE confirmed startup JSON on the gateway config volume; Caddy starts from that file and admin.config.persist=false disables its unsafe autosave. Caddy active JSON is the runtime confirmation witness. No separate desired-route registry exists. Changes serialize with a host gateway lock before an app install lock. Duplicate hostname ownership and foreign gateway/port/network/data are rejected. Before loading, leave the last confirmed startup file untouched. After an acknowledged/reconciled load, require active JSON exactly equals candidate, then write a separate temporary file, fsync it, atomically replace the confirmed startup file and fsync its directory. Never truncate/overwrite the prior startup file in place. Confirm saved JSON equals active before readiness. A successful Caddy HTTP response is insufficient. On interrupted update, startup reads the last complete confirmed JSON (old or newly committed); every previously confirmed other-app route survives.
5. **Certificates:** Caddy's ACME implementation owns issuance and renewal; certificate storage persists. Default issuer uses public ACME/system trust. Explicit private ACME/root-CA configuration may support organizational deployments and real protocol fixtures; it never disables hostname or certificate checking and never counts as public issuance. Issuer, email, ACME server and trusted-root policy must name exactly this app hostname; an unbounded/default policy may not modify other apps. DNS/challenge failure pauses with actionable steps then genuinely rechecks. Readiness requires an actual trusted TLS handshake and the correct HTTPS app health identity, not merely a running proxy process.
6. **Authorization and admission:** auth.py owns current DB session/active-role authorization and write Origin/CSRF checks. Multipart upload admission must resolve that same real identity before receiving/spooling bytes; a cookie's presence is not authentication. Revalidate at the actual write boundary because an account may be disabled during upload. Bound hashing concurrency and global/peer/name pressure before scrypt. Trust no arbitrary forwarded IP; keep one Uvicorn worker until limiter ownership is intentionally changed. Explicit 429 is rejection, not a retryable unknown write.
7. **Files:** retain the current durable-blob-before-metadata-COMMIT invariant, exact byte cap, temp UUID identity, and compensation only for proven uncommitted outcomes. Move blocking disk/SQLite work off the event loop. Committed blob bytes are immutable and are never permanently deleted; Trash retains them. This makes online snapshotting possible. Any future permanent deletion invalidates the backup model and must coordinate retention before introduction.
8. **Selected UI metadata:** server detail resources, keyed by app/account/resource/selection epoch, own selected Project/Conversation metadata. Add authenticated GET detail endpoints returning the already existing complete Project/Conversation shapes; enforce the same DM participant predicate as messages. Collections remain paginated sidebar summaries. Remove selected-ID automatic collection scans; do not use generic metadata or stale collection fallbacks when detail is missing. Late detail cannot replace another selection/account. Existing Notes/Task draft/revision owners remain unchanged.
9. **Backup worker:** one per-app source-built Python+Restic sidecar owns schedule, exclusive run lock, status/heartbeat, repository operation and retention. Mount app data read-only as UID10001; private work/status/secrets volumes, no Docker socket. Use the same source-built app image with a pinned Restic binary stage. Passwords/keys are private files, never argv, labels, logs or committed source. S3-compatible HTTPS storage is the initial off-host backend; a custom trusted CA is explicit. The configured repository base receives an automatic app+instance suffix so apps do not accidentally share one repository.
10. **Snapshot producer:** SQLite online backup first, bounded by a real deadline; validate schema/metadata/integrity/FKs. Enumerate Files blob keys from that frozen DB, including Trash; then stream exactly those immutable referenced bytes, runtime config and a checksum/provenance manifest. Verify config bytes before/after capture; missing/replaced/unsafe data fails. No full live DB file copy. No application downtime for scheduled backup. The installer stops and confirms the selected backup worker is stopped before a runtime/image transition, preventing concurrent provenance changes; it restarts/configures the worker afterward.
11. **Snapshot publication:** run Restic `backup --stdin-from-command --stdin-filename opensw.tar -- python ... emit`, never an unchecked shell pipe. Producer nonzero must prevent a completed snapshot. Exit3/incomplete/timeout is not success. Use a stable repository owner/host tag and a unique run tag for readonly reconciliation of unknown results. Do not replay an uncertain upload. A later scheduled snapshot is a new capture, not a replay of the old command. Preserve prior known backups after failure.
12. **Retention and health:** dedicated repository must contain only this app/instance's snapshots before pruning. Retention applies only after a new confirmed successful snapshot and uses stable host/path grouping (not unique run tags), keep-within configured days plus at least one latest snapshot. Foreign-owner snapshots/locks fail closed. Never globally unlock/delete unknown locks. Record heartbeat, last attempt/error, last successful snapshot and restore verification time atomically; Docker health/status become nonzero on failed/stale backup. First production setup requires a successful encrypted backup and integrity/restore validation. Periodic full restore verification must be scheduled with a documented default interval; ordinary intervening checks avoid downloading the entire repository each time.
13. **Restore:** only a new empty destination volume with the same app/instance; never overwrite the original. Verify authenticated Restic contents, safe relative archive paths/no links, checksum manifest, complete referenced blobs, metadata, integrity/FKs and schema. Revoke restored sessions. An explicitly selected new HTTPS origin may replace the saved origin; other identity/config changes are rejected. By default build the current selected app from the downloaded source; require the snapshot's exact supported schema1, app/instance, complete config and archive integrity, and preserve its recorded original image/source provenance without comparing artifact IDs for equality. An explicit existing-image override must validate selected app and supported schema. Start that verified image. Production-ready/user-switch confirmation follows readiness, actual trusted HTTPS and full app API/content proof. Public proxy admission can occur before the verifier; treat it as possible admission immediately and report degraded/noDBrollback on any later failure. No automatic DB rollback after accepted writes.
14. **Verifier:** tools/verify_api.py remains the canonical full HTTP route verifier and diagnostic owner. Public deployments must be verified through actual HTTPS with normal cookie/certificate checks, preserving Secure cookies. Private HTTP has its legitimate existing transport. New detail routes join the mechanically checked manifest. Keep the operator account/content untouched and mutate only confirmed namespaced fixtures. No automatic replay of unknown writes. All four apps need live restore/API proof, not Files-only recovery.
15. **Workload evidence/release:** reproducible actual HTTP/Docker runs, exact source/image/engine and resource limits, operation counts and latency distributions. No mocks as capacity evidence; no arbitrary success thresholds chosen after seeing results. Persistent per-actor HTTP clients reuse TLS connections as real browsers do; record client CPU separately from server/gateway/backup CPU and test new-connection/auth pressure separately. Application fixes require affected reruns, not stale prior-build evidence.
